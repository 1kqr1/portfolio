# 構成変更: 「LPっぽさ」の解消（2026-08-21）

## 経緯

フェーズ5完了後、本番公開したものを見た本人から「なんかLPになった?」という指摘があった。

実測したところ、当たっていた:

| セクション | 高さ | ページ全体に占める割合 |
|---|---|---|
| 名前・導入 | 334px | 5.8% |
| **Featured（紡シフト1件）** | **2,391px** | **41.2%** |
| Work（他2件） | 1,428px | 24.6% |
| Other（5件） | 714px | 12.3% |
| About | 435px | 7.5% |
| Contact | 322px | 5.5% |

全体7.2画面ぶんのスクロールのうち、**1案件だけで41%**を占めていた。英語のセクションラベル（Featured / Work / Other / About / Contact）、末尾のCTAボタンと合わせて、構造として完全にLPの型になっていた。

原因はフェーズ2で決めた「個別ページを作らず1ページに収める」という判断そのもの。当時は「採用担当が30秒で掴める」ことを優先したが、実物にすると「作品集」ではなく「1案件の売り込みページ」に見えた。

## 対応

3案（①1ページのまま先頭に一覧を置く／②個別ページに分ける／③見た目だけ調整）のうち、**②個別ページに分ける**を選択。ブランチ `restructure/works-pages` で作業。

### 構成変更

- トップページ（`/`）は**実績一覧が主役**になるよう作り直した。3案件を「課題文＋案件名＋要約＋タグ」の縦積みリストで並べ、各行から個別ページへ遷移する
- 各案件の詳細（課題→やったこと→技術的判断→結果）は `/works/{slug}/` に分離した
  - `/works/tsumugi-shift/`
  - `/works/intern-attendance/`
  - `/works/dcc-portal/`
- 「Featured」の特別扱いをやめ、3案件を対等に一覧できるようにした
- 英語のセクションラベル（Featured/Work/Other/About/Contact）を日本語に変更（実績／その他の制作物／私について／連絡先）

### 技術的な対応

`output: 'export'` のまま `generateStaticParams` で3件の詳細ページを静的生成した（動的ルーティングだが実体はビルド時に全て確定するHTML）。

複数ページ化に伴い、単一ページ前提だった2つのビルドスクリプトを直した:

- **`scripts/build-display-font.mjs`**: 見出し文字の収集を、`content/site.ts` の特定キーだけでなく**全文**、および `app/**/*.tsx` の**JSXテキストノードと文字列リテラル全体**から拾うように変更。ページ数が増えても、ハードコードした見出し文言（「実績」「私について」等）を手で追記する必要がなくなる
- **`scripts/verify-font-coverage.mjs`**: 検証対象を `out/index.html` 1枚から `out/` 配下の**全HTMLファイル**に拡張

### 検証結果

- クリーンビルドで7ページ生成（`/`、`/_not-found`、`/icon.svg`、`/works/{3件}`、`/404`）
- 見出しサブセット: 448字（1ページ構成時の145字から増加。複数案件ぶんの見出し文言が増えたため）
- 出力されたHTMLの `<script>` タグ: 全ページで **0個**（ハイドレーション除去は複数ページでも機能）
- 全ルートの疎通確認: `/`、3件の詳細ページとも200。存在しないパスは404（`out/404.html` が生成され、独自の404ページが表示されることを確認。簡易ローカルサーバーでは404ルーティングが効かない場合があるが、これはサーバー側の制約でありビルド成果物には問題無い）
- 375px幅で横スクロール無し、はみ出し要素0件
- 詳細ページ（紡シフト）: 見出し階層 h1→h2×5、シグネチャ要素（紙のスクショ）の静止transform、スクリプト0個をすべて確認
- スクショ無し・ライブリンク無しの案件（インターン勤怠システム）で、該当セクションが正しく非表示になることを確認（空のセクションが出ない）
- `out/` 合計サイズ: 950KB（画像・フォント込み、3ページぶんの詳細ページを含む）

このドキュメントはフェーズ5完了後の追加対応の記録。承認され次第 `main` にマージし、Cloudflare Pages へ反映する。

## 4. Next.js のハイドレーションJSを取り除いた判断（要確認）

### 何が起きたか

Next.js への移行を完了した直後（コミット `fcd871e`）の実測値は、**目標を大きく下回っていた**:

| | 移行直後 | 目標 |
|---|---|---|
| Performance | 87 | 95以上 |
| LCP | 4,124 ms | 2,000 ms未満 |
| 初期ロードJS | 565,290 B（gzip 172,362 B） | 旧サイト39,330 Bから削減 |

原因を調べたところ:

- 実ブラウザ（スロットリング無し）での LCP 要素は本文テキスト（`p.flagship__body`）で、**124 ms** で描画されていた。CLS は 0。
- Lighthouse の模擬スロットリング下では **LCP と TTI が 4,124 ms でぴったり一致**していた。つまりテキストの描画自体ではなく、**JS の実行完了を待たされている**状態だった。
- Lighthouse の指摘も `Reduce unused JavaScript: Est savings of 191 KiB`。
- 内訳を確認すると、最大のチャンク（229 KB）は **react-dom（ハイドレーション用）**。

このサイトは**クライアントコンポーネントを1つも持たない**（インタラクションが必要な箇所が無い設計）。つまりこの JS は「サーバーが生成したのと同一のマークアップを、ブラウザでもう一度描き直すだけ」で、画面上は何も変わらない。それが LCP を 4.1 秒まで押し下げていた。

### やったこと

ビルド後に `<script>` タグを取り除き、素の静的HTMLとして配信するようにした（`scripts/strip-hydration.mjs`）。リンクはすべて通常の `<a>` なので、これで壊れる機能は無い。

結果:

| | 除去前 | 除去後 |
|---|---|---|
| Performance | 87 | **100** |
| LCP | 4,124 ms | **1,504 ms** |
| 初期ロードJS | 565,290 B | **0 B** |
| 総転送量 | 559 KiB | **98 KiB** |

### 承知しておいてほしいこと

これは **Next.js が公式にサポートする使い方ではない**。将来インタラクションを追加したくなったときに問題になるので、次の安全装置を入れてある:

- `app/` `components/` `content/` を走査して `'use client'` を1つでも見つけたら、**除去処理を中止して警告を出す**（ビルドは通る）。
- その場合は `package.json` の build から `strip-hydration` の手順を外せば、通常の Next.js の挙動に戻る。

**より率直に言うと**: このサイトは Next.js の機能（クライアントサイドルーティング、サーバーコンポーネントの動的な組み立て、`next/image` の最適化など）をほぼ何も使っていない。1ページ・完全静的・インタラクション無しという最終的な仕様に対しては、Next.js はオーバースペックで、素の HTML/CSS のままか、あるいは Astro のような「既定でJSを出さない」構成の方が素直だった。Next.js 化はフェーズ1の確認で明示的に選ばれた方針なので**そのまま完遂した**が、この構成上のミスマッチは残っている。今後インタラクションを足す予定が無いなら、この点は認識しておいた方がいい。
