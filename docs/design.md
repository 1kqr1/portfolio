## 1. カラーパレット

現状（`css/style.css` の `:root`）を確認したところ、背景 `#0a0a0b`・アクセント `#e4e4e7`（ほぼ白のグレー）というモノクロ系ダークで、禁止リストの「ほぼ黒＋蛍光グリーン/朱色」そのものではないが、"ダーク＋グレー＋ガラス風"という、これはこれで量産型のdev系ポートフォリオの典型に入る。今回は**方向を反転させ、明るい紙質のエディトリアル系**を提案する。

| 名前 | Hex | 用途 |
|---|---|---|
| `paper` | `#EDEEEA` | 背景（クリーム寄りの `#F4F1EA` 系は禁止リスト該当のため、意図的に彩度を落とし緑灰よりに寄せた） |
| `ink` | `#1C1E1D` | 本文・見出しの主文字色 |
| `ink-soft` | `#63665F` | キャプション・メタ情報（日付・タグ）用の副文字色 |
| `line` | `#D8D9D3` | 罫線・区切り線（**使用箇所は最小限に絞る**。理由は5章の自己批評を参照） |
| `signal` | `#2B4C7E` | CTA・リンク・シグネチャ要素にのみ使う、唯一の強い色 |

**計5色。** 当初あった `signal-warm`（#A8763E、「結果の数値」用）は削除した。理由: フェーズ2の棚卸しの結果、**数値化された成果が実在しない**ため（紡シフト＝運用開始直後で定量データ無し／インターン勤怠＝不採用／DCCポータル＝定量測定なし）。使う当てのない色をパレットに置くと、実装時に「せっかくあるから」と本来不要な場所で使われて統一感を壊す。実在するコンテンツに存在しない色は最初から持たない。

「結果」パートの文字色は `ink`（本文と同じ）を使い、色ではなく**配置と余白**で区別する。

**禁止リストとの照合**:
- クリーム＋セリフ＋テラコッタ: `paper`はクリームより緑灰寄りに調整、セリフは日本語ミンチョ体（後述、欧文ハイコントラストセリフとは別物）、テラコッタ系オレンジは不使用（`signal-warm`は琥珀寄りの落ち着いた色）→ 該当しないが近い方向性ではあるため5章で再検証する。
- ほぼ黒＋蛍光色: 不使用（そもそも背景を明転させた）。
- ヘアライン罫線だらけ: リスクあり。使用箇所を意識的に絞る（5章）。

## 2. タイポグラフィ（実測に基づく）

日本語ウェブフォントは「ファイルが重い」と言われる通り、素朴に読み込むと1ウェイトの全文字（Noto Sans JP 400）で**フルサイズは約5.3MB**（実測、TTF）。ただしGoogle Fontsは通常のブラウザに対しては1ウェイトを**124個のunicode-range分割woff2**として配信し、ブラウザは実際にページ内で使われている文字を含むチャンクだけを取得する。日本語の「よく使う漢字＋ひらがな＋カタカナ＋句読点」に該当するチャンク群（実測、Noto Sans JP 400・chunk 113-119）を合計すると**約91.5KB**。同じ範囲をShippori Minchoで測ると約100KB、Zen Old Minchoで約98KB — ほぼ横並び。**見出し用途（使う文字数が少ない）に絞れば、実際のページ転送量は数十KB程度に収まる**、というのが実測結果。

この実測を踏まえた方針:

| 役割 | 書体 | ウェイト | 実測サイズの目安 | 備考 |
|---|---|---|---|---|
| ディスプレイ（見出し・課題文の見出し） | **Zen Old Mincho** | 400のみ | 見出しで使う文字数が少ないため、実際は数十KB程度（上記チャンクの一部のみ使用） | 日本語の明朝体。欧文の「ハイコントラストセリフ」とは別の文脈の書体で、禁止リスト1番目のクリーム×セリフの型には当たらない（4章で再検証） |
| 本文 | **システムフォント**（スタックは2-2節で確定） | - | **追加0KB** | フェーズ1調査の通り現状も日本語カスタムフォントは未使用。本文は文字量が多く変動も大きいため、Webフォント化のコスト効果が薄いと判断し、現状維持（ゼロコスト）を意図的に選ぶ |
| 数字・キャプション（タグ・日付・技術名） | **JetBrains Mono** | 400のみ・ラテン文字のみ | 実測 約31KB | 日本語グリフを持たないため対象外の文字には出現しない。技術タグ（"React"等）や日付・数値の桁を揃えるのに使う |

**追加フォント予算合計: 見出し数十KB + 本文0KB + キャプション31KB ≒ 現状のInter/Outfit（9ウェイト・38ファイル）を上回らない範囲**。`font-display: swap`を全書体に適用し、初期表示をブロックしない。

## 2-2. 本文フォントの実測比較（Windows優先での調整）

指示に従い、実際にブラウザ上でレンダリングして字面を計測した。

### 検証環境の限界（正直に記載）

このMacには **Hiragino Sans と YuGothic（macOS版の游ゴシック体）は存在するが、Windows固有の "Yu Gothic UI" と "Meiryo" は存在しない**ことを確認した（canvas での字幅比較により、これらの指定は全てデフォルトsans-serifにフォールバックしていることを実測）。

> 注: `document.fonts.check()` は上記4書体すべてに `true` を返したが、これはフォールバックでも `true` になる仕様で、インストール判定には使えなかった。字幅の実測で判定し直している。

したがって **「Windowsでの実際のラスタライズ（字の太さの見え方）」はこの環境では検証できていない。** 以下はmacOS上で取得した字面メトリクスの実測値と、そこから導ける調整方針であり、Windows実機での最終確認はフェーズ5に回す。

### 実測値（font-size 100px 時、単位px）

| | Hiragino Sans | YuGothic (Mac版) | Zen Old Mincho |
|---|---|---|---|
| 漢字「国」の字面高 | 87.5 | 85.5 | 86.9 |
| かな「あ」の字面高 | 86.2 | 83.2 | 81.8 |
| 欧文 x-height | 55.0 | 52.9 | **43.0** |
| 欧文 cap height | 77.1 | 75.5 | 72.6 |
| fontAscent | 88 | 88 | **116** |
| fontDescent | 12 | 12 | **29** |
| 欧文「Hxg」の字幅 | 200.4 | 178.2 | 173.9 |

### 実測から導いた調整方針

**① 游ゴシック系はヒラギノより小さく見える → Windows基準で本文サイズを決める**
かな字面で 83.2 vs 86.2（約3.5%小）、欧文字幅で 178.2 vs 200.4（約11%狭）。同じ `font-size` 指定でも游ゴシック環境の方が小さく・スカスカに見える。**閲覧者はWindowsが多い前提**なので、**游ゴシックで適正に見えるサイズを基準に決め、ヒラギノ側が少し大きく見えるのを許容する**（逆にするとWindows側が読みにくくなる）。本文の基準サイズは `17px` 程度から始めてフェーズ4で調整する。

**② Windowsの游ゴシックは細く見える問題への対策**
これは今回の環境では実測できていない既知の問題（Windows版 Yu Gothic の Regular はブラウザ上で細く描画される）。対策として、フォントスタックの先頭付近に **BIZ UDPGothic**（Windows 10 1809以降に同梱）を置く案を採る。ただし**全Windows環境での同梱状況は未検証**のため、フォールバックを厚めに用意する:

```css
--font-body:
  "Hiragino Sans",        /* macOS: 実測で最も字面が大きく読みやすい */
  "BIZ UDPGothic",        /* Windows: 游ゴシックの細さ回避（同梱状況は要実機確認） */
  "Yu Gothic UI",         /* Windows: 上記が無い場合 */
  "YuGothic", "Yu Gothic",
  "Meiryo",               /* さらに古い環境 */
  sans-serif;
```

**③ 明朝見出しと本文の相性 — 行間を別々に指定する必要がある（実測で判明）**
Zen Old Mincho は fontAscent 116 / descent 29（合計145）に対し、ヒラギノ・游ゴシックは 88/12（合計100）。**同じ `font-size` でも明朝見出しは約45%高い行ボックスを占める。** 見出しに本文と同じ `line-height` を与えると間延びするため、**見出しは `line-height: 1.4` 前後まで詰め、本文は `1.9` を基準にする**、と別々に指定する。

**④ 明朝見出しの中の欧文が小さくなる（実測で判明）**
Zen Old Mincho の欧文 x-height は 43.0 で、ヒラギノの 55.0 に対して約78%しかない。見出しには「LINE」「Excel」「DCC」など欧文が実際に含まれるため、**和文に対して欧文だけ明らかに小さく見える**。フェーズ4で実際に組んでから、必要なら見出し内の欧文サイズを微調整する（フェーズ5の確認項目に含める）。

**和欧混植のその他の方針**:
- 見出し（Zen Old Mincho）は明朝体の性質上、字間をわずかに開ける（`letter-spacing: 0.02〜0.04em`）。
- 本文に負の`letter-spacing`（欧文フォントでよくある詰め組み）は使わない。漢字を詰めると窮屈になる。

## 2-3. 角丸（この方向性のために決め直したもの）

現行の `--radius-*` の踏襲はやめ、以下3値のみを定義する。**それ以外の場所では角丸を使わない。**

| 変数 | 値 | 使用箇所 | その値にした理由 |
|---|---|---|---|
| `--r-sheet` | `0` | フラッグシップのスクリーンショット（シグネチャ要素） | 実物の紙は角が丸くない。ここだけは「物体」として見せたいので、角丸をゼロにして紙の矩形をそのまま出す |
| `--r-tag` | `3px` | 技術名タグ・キャプションのラベル | ゼロにすると罫線だらけの新聞風（禁止リスト該当）に寄る。文字を囲う小さな要素にだけ最小限の丸みを持たせ、"罫線"ではなく"ラベル"として読ませる |
| `--r-action` | `6px` | CTAボタン・お問い合わせボタン | このサイトで唯一「押せる」要素であり、周囲の静的な要素と触覚的に区別する必要がある。3pxでは差が出ず、8px以上は今回の硬質な方向性から浮くため6px |

区切り線（`line` 色の水平線）には角丸の概念が無いため対象外。カード的な箱を作らない方向性のため、"カードの角丸"という用途自体が発生しない。

## 4. シグネチャ要素

**フラッグシップ（紡シフト）のスクリーンショットだけを、「机の上に置かれた一枚の紙」のように見せる。** わずかな影と1〜2度の傾き、それだけ。他の全要素（その他の実績・その他の制作物・About）は完全にフラットで、影も傾きも一切使わない。

**この要素は完全に静止させる。** 傾きも影も固定値で、スクロールでもホバーでも一切動かさない。`prefers-reduced-motion` で無効化する対象ですらない（そもそもアニメーションを持たないため）。CSSとしては `transform: rotate(-1.2deg)` と `box-shadow` を静的に当てるだけで、`transition` も付けない。

大胆さはこの1箇所だけに使い、それ以外（ナビゲーション・その他の実績のリスト・About・Contact）は罫線もシャドウも最小限のフラットな静けさに統一する。

### この意図をサイト上に書かない

紙のモチーフには「確定シフトを印刷して上司に渡していた」という本人の実話が背景にあるが、**この理由付けをサイト上に文章として載せることはしない。** デザインの意図を説明するキャプションや注釈は一切添えない。背景が伝わるかどうかは見た人次第で、伝わらなくてよい。この記述は制作側の判断根拠としてこのドキュメントに留める。

## 6. 自己批評

「同じ依頼を受けた別のAIが同じ答えを出しそうか」を検証する。

**最初に書いた案の問題点**: 実は最初に考えたのは「クリーム背景＋明朝体の大見出し＋テラコッタ系アクセント」で、これは禁止リストの1番目（クリーム×セリフ×テラコッタ）の**日本語版**にほぼ一致してしまっていた。禁止リストは欧文フォント・欧文配色を前提に書かれているため、「日本語に翻訳すれば別物」と自分を納得させかけたが、配色の骨格（暖色系の明るい背景＋高コントラストなセリフ見出し＋暖色アクセント）が同じである以上、これは体のいい抜け道でしかない。

**変えた点**:
1. `paper`をクリームの暖色域（#F4F1EAに近い黄み）から、意図的に緑灰よりの寒色寄り（#EDEEEA）にずらした。
2. アクセントカラーをテラコッタ系オレンジ（暖色）から、寒色のインクブルー（`signal` #2B4C7E）に変更した。**承認時の指示により、暖色アクセント `signal-warm` は完全に削除した**（1章参照）。
3. 装飾としてのセリフ体ではなく、"本人が語った紙の運用実態"に紐づけた「1枚のスクリーンショットだけを紙のように見せる」という、コンテンツに根拠のある大胆さ（4章）に変更し、色や書体だけで差別化しようとする姿勢自体をやめた。

**この論点は承認時に「現状の差別化で十分・方向性は変えない」と判断されたため、これ以上の検討は行わない。**

### B. 撤去では足りず、実装時に別途対応が必要なもの

| 原因箇所 | なぜ撤去だけでは済まないか | フェーズ4での対応方針 |
|---|---|---|
| **`scroll` イベントリスナー**<br>[js/app.js:183](js/app.js#L183)（navbarに `.scrolled` を付与） | ナビゲーション自体は新デザインにも残るため、「消す」だけでは済まない。かつフェーズ4のルールで `scroll` リスナーは**使用禁止** | **navをスクロール反応させない静的な要素にする**（背景色を最初から不透明にし、状態変化を持たせない）。これで `scroll` リスナーが1つも要らなくなる。もし視覚的に区切りが必要なら、`position: sticky` + 常時表示の下罫線で対応し、JSは使わない |

### C. フェーズ4に持ち越す確認事項
